# Додаток до PRD

Технічна глибина для наступних кроків (архітектура, UX). Не є частиною вимог — це напрям і
контекст. Основа — `../../briefs/brief-untitled-2026-08-31/addendum.md`.

## Технічний напрям

- **Мова:** повністю JavaScript/TypeScript — обрано за низький поріг розгортання та легку
  передачу іншому волонтеру (NFR-4).
- **Фронтенд:** React (вказано користувачем). SPA або SSR — на розсуд архітектури.
- **Бекенд:** Node (вказано користувачем). Рекомендація: звичайний REST API (Express або
  NestJS) з реляційною БД.
- **База даних:** PostgreSQL — предметна область сильно реляційна й має похідні обчислення
  (Таблиця групи, Сітка).
- **Автентифікація:** Google OAuth / OpenID Connect. Сесія або JWT. Роль Адмін — прапорець
  у таблиці користувачів; перший Адмін через міграцію/сід.
- **Хостинг:** «легко піднімається» — один контейнер / Docker Compose або керована платформа
  (Render, Railway, Fly.io) з керованим Postgres. Безкоштовний/дешевий тариф (§6.2).
- **Бекапи:** автоматичний щоденний дамп БД у зовнішнє сховище (напр. bucket); утримання
  щонайменше 30 днів (NFR-7). Деталі — етап архітектури.
- **Локалізація:** статичні українські рядки в коді; окрема бібліотека i18n не потрібна (одна
  мова, NFR-2, Не-ціль «кілька мов»).

## Ескіз моделі даних (орієнтовний, не нормативний)

```
Discipline            (CLASSIC | BEACH — enum, не таблиця; BEACH неактивна)
Tournament            id, discipline, type, name, year, state,
                      scoring_preset, team_count, rounds
                      -- v1: рівно одна Group на Tournament; groups_count зʼявиться з багатогруповим форматом
Team                  id, name                          -- багаторазова ідентичність
TournamentEntry       id, tournament_id, team_id        -- унікально (tournament_id, team_id)
Player                id, entry_id, full_name,           -- лише full_name обов'язкове
                      birth_date?, birth_place?, sport_rank?, position?, height?, weight?
Group                 id, tournament_id, name
GroupSlot             group_id, entry_id                -- склад групи
Match                 id, tournament_id, stage(GROUP|SEMIFINAL|THIRD_PLACE|FINAL),
                      group_id?, home_entry_id, away_entry_id,
                      scheduled_at?, venue_text?, played(bool)
SetScore              match_id, set_no, home_points, away_points
User                  id, google_sub, email, name, is_admin
```

- **Таблиця групи** не зберігається як таблиця БД — обчислюється з `Match` + `SetScore` за
  `scoring_preset`. Можна кешувати матеріалізованим представленням, якщо знадобиться.
- **Плейоф-пари** живуть у `Match` зі `stage` ≠ GROUP; `home/away_entry_id` для Фіналу й
  Матчу за 3-тє місце заповнюються тригером/сервісом після внесення півфіналів (FR-20).
- Модель свідомо лишає місце під: `discipline = BEACH`, `stage`-значення для нокаут-сітки
  довільного розміру, `Team` у кількох `TournamentEntry` різних турнірів.

## Двигун підрахунку — примітки для реалізації

- Вхід: усі зіграні `Match` Групи + `scoring_preset`.
- Крок 1 — очки за матч:
  - `CLASSIC`: 3:0/3:1 → (3, 0); 3:2 → (2, 1).
  - `CUSTOM`: очки = кількість виграних партій кожної сторони (сума завжди 3).
- Крок 2 — агрегати на команду: зіграно, П, Пор, очки, партії +/−.
- Крок 3 — сортування: очки ↓ → особиста зустріч (міні-таблиця очок серед команд, що
  зрівнялися) → виграні партії ↓ → назва команди ↑ (детермінований резерв) з прапорцем
  `needs_manual_tiebreak`.
- Перерахунок синхронний при кожному `create/update/delete` `Match`/`SetScore`; обсяги
  дозволяють.

## Валідація рахунку (чернетка правил, підтвердити)

Цільовий рахунок партії `target` залежить від Типу турніру: Ветеранський чемпіонат → 15,
решта → 25. У Класичному вирішальна 5-та партія завжди до 15.

- `CLASSIC`: 3–5 партій; переможець має рівно 3 виграні партії; партії 1–4 до `target`
  (різниця ≥ 2), партія 5 до 15 (різниця ≥ 2); верхня межа рахунку не обмежена.
- `CUSTOM`: рівно 3 партії; кожна до `target` з різницею ≥ 2; підсумок 3:0 або 2:1.

Якщо з'являться інші значення `target` — винести його в явне поле `Tournament` замість
похідного від типу (Відкрите питання №5 PRD).

| Створити турнір з правилами | FR-4, FR-5 |

| Проставити дату/час/зал | FR-13 |
| Внести й виправити рахунок | FR-15, FR-16 |
| Автоматична таблиця | FR-17 |
| Сформувати плейоф | FR-19 |
| Автофінал / матч за 3-тє | FR-20 |
| Завершити → архів | FR-7, FR-23 |

| Можливість (UJ-2) | FR |
|---|---|
